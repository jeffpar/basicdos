**NOTE**: This is a design document for work in progress on the `mmu` branch.  Everything here is tentative; [Phase 1](#phases) has been implemented, CPU$ now manages all memory on every processor (see [The CPU$ Driver](#cpu)), and on an 80286, BASIC-DOS switches to protected mode while its drivers initialize, and stays there: the kernel initializes, and COMMAND.COM starts and runs commands and some programs, in protected mode (see [Protected-Mode Initialization](#pminit)).  The [Protected Mode demo](/demos/mmu/) boots that way on a 2Mb PC AT, and its [Debugger](/demos/mmu/debugger/) page adds the PCjs Debugger (see [The Protected Mode Demo](#pmdemo)).

### Goals

- Let BASIC-DOS use the extended memory and protected mode of an 80286 or 80386 (with its drivers and kernel at ring 0, its sessions at ring 3, and extended memory for BASIC programs), while the same binaries still run on an 8086 or 8088 (with no extra memory used there).
- Keep all knowledge of descriptors, selectors, and physical memory in one built-in driver, **CPU$**, which loads first, determines the processor type, and on a protected-mode processor, manages a physical memory arena and the GDT, IDT, and LDT.
- Restructure the rest of BASIC-DOS (drivers, kernel, and COMMAND.COM) so that it can run in either mode, using CPU$ to map existing blocks of code and data to selectors, and to allocate and free extended memory.

### Target and Test Machines

The design targets the IBM PC AT: `ibm5170` (80286, AT BIOS revision 3) with `--ram=2M`, which pc.js now splits into 640K of conventional memory (0-9FFFFh) and 1408K of extended memory (100000h-25FFFFh), like the PCjs 2048K PC AT machines.  On the `mmu` branch, [boot.sh](../../../boot.sh) passes `--ram=2M` for every configuration.

Every change is tested on four machines, with `tools/tests/mmutest.sh`, which runs quick.sh's floppy tests and CPUTEST on each:

| Name | Machine | CPU$ |
|------|---------|------|
| `8088` | IBM PC XT (`ibm5160`) | The 8086 CPU$ stays (CPU type 0, hardware type 0) |
| `real` | 2Mb PC AT with `CPU=8088` in CONFIG.SYS | The 8086 CPU$ stays (CPU type 0, hardware type 2), so BASIC-DOS runs in real mode with A20 disabled |
| `pm` | 2Mb PC AT without `CPU=8088`, with `RING=0` | Switches to protected mode (see [Protected-Mode Initialization](#pminit)), with programs at ring 0, where every test runs: DOSTESTS checks that an MZ EXE file is refused (its pipeline reservation test needs one; see [Code Aliases](#aliases)), and HARDERR skips its direct INT 13h read of a recovered metadata sector, since the diskette BIOS can't reach a protected-mode program's memory (see INT 13h in [Protected-Mode Interrupts](#interrupts)) |
| `r3` | 2Mb PC AT without `CPU=8088` | The same, but with programs (and COMMAND.COM) at ring 3, as by default (see [Running Programs at Ring 3](#ring3)), where CPUTEST (which calls CPU$ directly) and HARDERR's INT 13h hook tests report that they're skipped |

Because real mode is the only mode they've been tested in, every other configuration that boots on a PC AT or DeskPro 386 (the demo diskettes and hard disk, the test configurations that boot.sh uses, and mk.sh's build configuration) has `CPU=8088` in its CONFIG.SYS; only the `pm` and `r3` tests, `tools/tests/pmboot.sh`, and the Protected Mode demo leave it out.  The 80386 path (which returns from its self-test to real mode by clearing PE instead of resetting the CPU) is still tested occasionally with `compaq386` (a COMPAQ DeskPro 386), but only the PC AT is a target for now.

### The CPU$ Drivers {#cpu}

CPU$ manages all memory, on every processor, so BASDEV.COM starts with two CPU$ drivers, of which exactly one stays loaded (a device name only has to be unique among the drivers that stay, since only they are linked into the chain): the 80286 driver (286dev.asm), followed by the 8086 driver (x86dev.asm).  The 80286 driver, which is initialized first, determines the processor type:

1. An 8086 or 80186 decrements SP before PUSH SP stores it, whereas an 80286 or later stores the original value.
2. An 80186 masks shift counts to 5 bits, so shifting 1 left 33 times leaves 2 (instead of 0 on an 8086).
3. In real mode, an 80286 always clears FLAGS bits 12-15, whereas an 80386 lets software set bits 12-14 (IOPL and NT).

It stores the result in CPU_HWTYPE (0:513h) and CPU_TYPE (0:512h), as one of the CPUTYPE_* values in cpu.inc (0 = 8086/8088, 1 = 80186/80188, 2 = 80286, 3 = 80386 or later).  A `CPU=8088` line in CONFIG.SYS, or less than 128K of conventional memory (after any `MEMSIZE=` line), makes CPU$ store 0 (8086/8088) in CPU_TYPE and act as it does on an 8088, without enabling A20; CPU_HWTYPE is still the processor's own type, for software that must know how the processor runs instructions (eg, DEBUG.COM's disassembler).

Neither CPU$ can be skipped (devinit ignores `SKIP=CPU$`).  The one that stays makes its functions available through DDINT_CPU (0050:0030h), a 5-byte far jump in low memory like the other DDINT entry points, which devinit initializes to `STC`, `RETF`, so that a call fails (with carry set) until CPU$ initializes:

- **The 80286 driver** stays if the processor is an 80286 or later, there's at least 128K of conventional memory (after any `MEMSIZE=` line), the BIOS reports at least 64K of extended memory (INT 15h function 88h), A20 can be enabled (with the 8042 keyboard controller, as on a PC AT), and a switch to protected mode and back succeeds.  It keeps everything but its initialization code (about 3K), enables A20 permanently, and builds its [arena](#arena) (a table of PMBs) and descriptor tables in the 64K system area.  Otherwise (or with `CPU=8088`), it unloads itself, and devinit moves the drivers after it down (see [Claiming Memory at Boot](#claiming)), so whichever driver stays is at 0970h.
- **The 8086 driver** stays unless CPU$ is already loaded.  It manages memory with a chain of MCBs, as DOS always has, starting in the paragraph after its code (about 1K), so every block that's allocated after it (eg, the other drivers, the kernel, and programs) has an MCB in the paragraph before it, which programs that walk the MCB chain can see.

The 80286 driver, which always initializes first, also applies any `MEMSIZE=` line (see [CONFIG.SYS](../../bdman/cfg/#memsize)), by lowering the BIOS's MEMORY_SIZE (which INT 12h returns), so either driver's arena ends there.  Either way, devinit claims what it's using as soon as CPU$ initializes (see [Claiming Memory at Boot](#claiming)).

The one that stays also provides DDINT_GETVEC and DDINT_SETVEC (see [Device Drivers](../dev/)), which devinit also initializes to `STC`, `RETF`: the 8086 driver points them at its own code (which reads and writes the vector table) when it initializes, and the 80286 driver at its protected-mode code when it switches to protected mode (see [Protected-Mode Initialization](#pminit)), so either way, before any other driver initializes.

#### Functions

Call DDINT_CPU with a function number in AH.  Physical addresses and lengths are 32-bit byte values: addresses in DX:CX and lengths in SI:DI (high:low).  Every function runs with interrupts disabled, preserves BX, SI, DI, BP, DS, and ES, and returns carry clear on success, or carry set with an error code in AX.

| AH | Function | Inputs | Outputs |
|----|----------|--------|---------|
| 00h | CPU_GETINFO | | AL = CPU type, AH = CPUF_* flags (bits 6-7 = CPU_HWTYPE), DX:CX = length of largest free block |
| 01h | CPU_ALLOC | AL = MEMF_* flags, BX = owner, SI:DI = length | AX = first selector (0 if MEMF_NONE), DX:CX = address |
| 02h | CPU_FREE | DX:CX = block | |
| 03h | CPU_MAP | AL = MEMF_* flags, DX:CX = address, SI:DI = length | AX = first selector, CX = number of selectors |
| 04h | CPU_UNMAP | BX = first selector, CX = number of selectors (0 = 1) | |
| 05h | CPU_QUERY | BX = PMB number (0 = first), or -1 for block DX:CX; ES:DI -> 32-byte buffer | PMB copied to ES:DI |
| 06h | CPU_ALIAS | AL = MEMF_* flags, BX = selector | AX = new selector, DX:CX = base address |
| 07h | CPU_PMODE | (none) | Protected mode, for good: CS, DS, ES, and SS are now selectors for the same memory, and AX = a data selector for the caller's CS (see [Protected-Mode Initialization](#pminit)) |
| 08h | CPU_REALLOC | DX:CX = block, SI:DI = new length | |
| 09h | CPU_MOVE | ES:BX -> MOVEPKT (source address, destination address, and length, all dwords) | |
| 0Ah | CPU_SETBLK | DX:CX = block, AL = MCBTYPE_*, BX = owner (non-zero), ES:SI -> 8-character name (SI = 0 for none) | |
| 0Bh | CPU_FREEALL | BX = owner | |
| 0Ch | CPU_SETLIM | BX = selector, SI:DI = new length (1 to 64K) | |
| 0Dh | CPU_SEGINFO | AL = ADDR_* flags, BX = selector (or segment) | DX:CX = base address, AX = limit (or with ADDR_RIGHTS, AL = access rights, AH = extended byte) |
| 0Eh | CPU_RWMEM | AL = ADDR_* flags, BX:SI = address, CX = length, ES:DI -> buffer | |
| 0Fh | CPU_SYSREGS | ES:DI -> 12-byte buffer | GDTR and IDTR stored at ES:DI; AX = MSW, CX = LDTR, DX = TR |
| 10h | CPU_SETFAULT | DX:CX = fault handler (0:0 for none) | DX:CX = previous handler |
| 11h | CPU_SETSTACK | DX:CX = ring 0 stack (SS:SP) | DX:CX = previous ring 0 stack |
| 12h | CPU_SETLDT | AL = session number | |

A *block* (DX:CX) is the address that CPU_ALLOC returned, or DX = -1 and CX = the selector (or segment) that it returned, which is what DOS has (eg, in ES for DOS_MEM_FREE).  CPU_SETBLK records a block's owner, type, and name for DOS (in PMB_OWNER, PMB_MCBTYPE, and PMB_NAME, or with the 8086 driver, in the block's MCB), which MEM and DEBUG's DM show; CPU_FREE and CPU_FREEALL clear them, and CPU_FREEALL frees every block that an owner has (DOS uses it when a program ends).  An owner is a PSP's selector, and an LDT selector names a PSP only in its own session's LDT (another session can have a PSP with the same selector), so for an owner that's an LDT selector, CPU_FREEALL frees only the blocks whose PMB_LDT (the LDT that was active when CPU_ALLOC or CPU_SETBLK set the owner) is the active LDT.

MEMF_LDT (01h) requests LDT selectors instead of GDT selectors, MEMF_CODE (02h) requests execute/read code segments instead of read/write data segments, MEMF_NONE (04h) makes CPU_ALLOC allocate memory without any selectors (for CPU_MAP and CPU_ALIAS, the same bit is MEMF_CONFORM, which with MEMF_CODE makes conforming code, which code at any ring can call, and which runs at the caller's ring, as FPU$'s functions do), MEMF_RDONLY (08h) makes data read-only (or code execute-only), and MEMF_USER (10h) makes the selectors DPL 3 (for programs at ring 3) instead of DPL 0.  CPU_ALLOC also takes MEMF_LOW (20h) to allocate below 1Mb, MEMF_HIGH (40h) to allocate from the top of the last free block that's big enough, and MEMF_AT (80h) to allocate the memory at DX:CX (which must be free); otherwise, it allocates from anywhere in memory, conventional or extended (as DOS_MEM_ALLOC does).  CPU_ALIAS creates a new selector, with the access rights that its MEMF_* flags select, for the same memory as an existing one (it copies the base and limit), and CPU_UNMAP frees it; see [Code Aliases](#aliases).  CPU_SETLIM changes the length that a selector covers (its limit), keeping the selector, so that anything that already holds it (eg, a driver's header, the driver chain, and IDT gates) sees the change; fixed GDT selectors can't change.

Every function works the same way in either driver and in either mode, so callers needn't check which is which: in real mode, CPU_ALLOC, CPU_MAP, and CPU_ALIAS return the memory's segment instead of a selector (CPU_ALLOC returns 0 for a block above 1Mb, and CPU_MAP fails with ERR_INVALID unless the memory is below 1Mb and paragraph-aligned), a segment is its own alias, and CPU_UNMAP has nothing to do.  CPU_REALLOC changes a block's length (rounded up to a multiple of 16): a shorter block frees its end, and a longer one takes what it needs from the next block, which must be free and long enough (ERR_NOMEMORY otherwise, with the block unchanged); its selectors don't change.  CPU_MOVE copies any amount of memory between two physical addresses, correctly even if the source and destination overlap; in real mode, both must be below 1Mb.  With the 8086 driver, every block has an MCB in the paragraph before it, so CPU_ALLOC with MEMF_AT needs that paragraph to be free too, and CPU_QUERY describes each MCB with a PMB (whose PMB_SEL is the block's segment).  A block of more than 64K gets one selector for every 64K (each 8 more than the last, so that `selector + 8 * n` addresses the *n*th 64K), and the last one's limit covers the rest.  CPU_ALLOC rounds lengths up to a multiple of 16, so every block starts on a paragraph boundary; CPU_MAP maps exactly the requested length.  Errors are ERR_INVALID (bad function, zero length, unknown PMB, a selector that can't be unmapped, or one that isn't in use for CPU_ALIAS), ERR_NOMEMORY (no block big enough, with DX:CX = length of the largest free block; or no free PMB or descriptors), and ERR_BADADDR (a block that CPU_ALLOC didn't return, for CPU_FREE, CPU_REALLOC, CPU_SETBLK, or CPU_QUERY).

CPU_SETFAULT gives a fatal protected-mode exception to a handler, before the 80286 driver reports it and stops the machine, unless it occurred in CPU$ or in the handler's own code.  In protected mode, the kernel sets the first handler (`dos_fault`, the last of its resident code, which it keeps only in protected mode) before CONFIG.SYS's DEVICE= drivers are loaded, and a debugger that sets its own (eg, DEBUG.COM) passes on the exceptions it doesn't trap to the handler it replaced (see [Protected-Mode Interrupts](#interrupts)).  The handler is entered with the registers as they were, interrupts disabled, and SS:SP pointing to a far return address, the vector, the error code, and an interrupt frame for the faulting instruction; for a software interrupt with no handler, those are its vector (0FFh if unknown), the caller's AX, and the INT itself.  A handler that can't handle the exception declines it by returning (RETF) with the registers and stack as they were, and then CPU$ reports it (`CPU fault vv (EC=xxxx) at cccc:iiii`, followed by `System halted`).  A handler that passes an exception on can replace the return address with its own, to find out whether the next handler declined it (as DEBUG.COM does, so that it can stop first).  Before stopping the machine, CPU$ offers the halt to the handler, as the same exception (with the same registers) but with FAULT_HALTED (80h) in the vector's high byte: a debugger can accept it by never returning (DEBUG.COM keeps control, with interrupts disabled), and any other handler declines it (as the kernel's does, since it already found the exception fatal), after which CPU$ stops the machine (HALT_FATAL).  The 8086 driver keeps the handler too, but never calls it, since real-mode exceptions go through the vectors.

CPU_SETSTACK sets the ring 0 stack (SS:SP) that the processor switches to when an interrupt or exception takes ring 3 code to ring 0, and returns the previous one.  The 80286 driver keeps it in its TSS (SEL_TSS), which CPU_PMODE loads; until a caller sets a stack, it's 0:0, so nothing can run at ring 3 (see [Running Programs at Ring 3](#ring3)).  The 8086 driver returns ERR_INVALID, since there's no ring 3 in real mode.

CPU_SETLDT makes the LDT of the session in AL the active one, so that the selectors the descriptor functions allocate with MEMF_LDT, free, and resolve (eg, for CPU_SEGINFO, or a block's selector for CPU_FREE) are in that session's LDT: each session has its own LDT (see [The System Area](#sysarea)), so that a program can't name another session's memory.  The kernel calls it whenever a different session becomes current (see [Running Programs at Ring 3](#ring3)).  In real mode (and in the 8086 driver) there are no LDTs, so it does nothing.

CPU_SEGINFO, CPU_RWMEM, and CPU_SYSREGS are for debuggers (eg, [DEBUG.COM](../../bdman/cfg/#device)), so they never change CPU$'s state, and work even when CPU$ itself was interrupted (eg, at a breakpoint in CPU$); CPU_RWMEM borrows a scratch selector, and restores its descriptor afterward.  An address (*segment*:*offset*) is in real-mode form, unless ADDR_SEL (01h) is set, in which case its segment is a protected-mode selector, in either mode: any present descriptor in the GDT (including the identity selectors) or the LDT.  With ADDR_PHYS (04h), the address is a physical address instead (its "segment" holds bits 16-31), which the 8086 driver accepts only below 1Mb.  With ADDR_RIGHTS (08h), CPU_SEGINFO returns a selector's access rights byte in AL and its descriptor's extended byte in AH, instead of its limit (zero for a real-mode segment), for a debugger's DS command; the access rights can't go in another register, since cpu_entry restores every register but AX, CX, and DX.  CPU_SEGINFO returns a segment's base address and limit (FFFFh for a real-mode segment).  CPU_RWMEM copies CX bytes from the address to ES:DI, or with ADDR_WRITE (02h), from ES:DI to the address, which must be within the segment's limit (and in real mode, below 1Mb); it writes through a data selector of its own, so it can store a breakpoint in a code segment.  CPU_SYSREGS stores the GDTR and IDTR as SGDT and SIDT do (a 16-bit limit and a 24-bit base, in 6 bytes each), and returns the MSW, LDTR, and TR (the last two are zero in real mode).  The 8086 driver accepts only real-mode addresses, and CPU_SYSREGS returns ERR_INVALID, which also tells a debugger that the processor has only one mode.

CPUF_HWTYPE (C0h) holds the processor's own type (CPU_HWTYPE, in bits 6-7), which AL (CPU_TYPE) understates with `CPU=8088`.  CPUF_PMOK (02h) means the protected-mode self-test passed (so the 80286 driver stayed, and CPU_PMODE is available), and CPUF_PM (01h) means that the processor is running in protected mode (after CPU_PMODE).  Like every other function, CPU_MOVE runs with interrupts disabled, so long moves delay interrupts.

In protected mode, the same functions will be reached through a call gate (SEL_CPU, below), so callers will do `call SEL_CPU:0` instead of calling DDINT_CPU.

**Why DDINT_CPU**: an IOCTL interface (like FPU$'s IOCTL_GETFPU) would make every caller open the device, and the callers will mostly be the kernel and other drivers.  DDINT_UTIL is the DOS's entry point for drivers, so it isn't available until sysinit, and it's the wrong direction (CPU$ is called *by* the DOS).  A software interrupt would work in both modes, but uses up a vector; the call gate gives protected-mode callers the same kind of fixed far address that DDINT_CPU gives real-mode callers.

### Memory Map (tentative)

Physical memory on the baseline 2Mb PC AT:

| Address | Length | PMB type | Contents |
|---------|--------|----------|----------|
| 000000h | 1K | USED | Real-mode interrupt vector table |
| 000400h | 256 | USED | ROM BIOS data area (segment 40h) |
| 000500h | 1136 | USED | BASIC-DOS low memory (also segment 40h, from offset 100h): CPU_TYPE (512h), CPU_HWTYPE (513h), CPU_ARENA (514h, the address of CPU$'s arena, for debuggers), the diskette parameter table (522h), the DDINT entry points (530h, called through segment 50h, starting with DDINT_CPU at 0050:0030h), and two disk buffers |
| 000970h | | USED | Drivers: CPU$ (first), NUL, VKD$, ..., then BASDOS.COM and its tables |
| | | FREE | The rest of conventional memory, for CPU_ALLOC (including DOS's blocks, eg, programs) |
| 0A0000h | 384K | RSVD | Video memory, adapter ROMs, and the system ROM (not RAM) |
| 100000h | 64K | SYS | CPU$ system area (the HMA; see below) |
| 110000h | 1344K | FREE | The rest of extended memory, also for CPU_ALLOC (and DOS) |
| 260000h | | | End of memory |

The PMB types (PMBTYPE_* in cpu.inc) are FREE (0), USED (1, allocated by CPU_ALLOC), SYS (2), and RSVD (3).  The end of conventional memory comes from the BIOS (MEMORY_SIZE), so a machine with less than 640K (or a `MEMSIZE=` line) has a larger RSVD block.  The 80286 driver starts with conventional memory in three PMBs (USED below the drivers, USED for CPU$ itself, and FREE for the rest), and devinit and sysinit [claim](#claiming) what they use; after that, DOS allocates from it with CPU_ALLOC like anything else (MEMF_LOW, for now).

#### The System Area {#sysarea}

CPU$ keeps everything it owns, other than its code, in the first 64K of extended memory, which (with A20 enabled) is addressable in real mode as segment FFFFh, and in protected mode with selector SEL_SYS, whose base is FFFF0h, so the same offsets work in both modes.  Its code is the same in both modes, too: it gets its data segment from the mode (SMSW), and never writes through CS.

| Offset | Linear | Contents |
|--------|--------|----------|
| 0000h | 0FFFF0h | Last 16 bytes of the ROM BIOS (unusable) |
| 0020h | 100010h | SYSVARS: signature, CPU type and flags, the PMB table's offset, count, and maximum, function arguments, saved real-mode SS:SP and CS, and the GDTR and IDTR values |
| 00D0h | 1000C0h | CALL 5 trampoline: `JMP 0000:00C0h` (see below) |
| 00E0h | 1000D0h | GDT: 256 descriptors that CPU$ allocates from (the fixed ones first) |
| 08E0h | 1008D0h | PMB table (128 entries of 32 bytes) |
| 18E0h | 1018D0h | `pm_call`'s IDT (256 gates, for the self-test, which return to real mode) |
| 20E0h | 1020D0h | The protected-mode IDT (256 gates; see [Protected-Mode Interrupts](#interrupts)) |
| 28E0h | 1028D0h | LDTs: one for each of 32 sessions, 96 descriptors (300h bytes) each, so session *n*'s is at 28E0h + *n* * 300h (see CPU_SETLDT) |
| 88E0h | 1088D0h | TSS (44 bytes, 80286 format), only for its ring 0 stack (see CPU_SETSTACK) |
| 890Ch | 1088FCh | Unused (zero), up to the identity selectors |
| A0E0h | 10A0D0h | GDT: identity selectors A000h-F800h, every 800h (8 bytes each, zero in between), through 10F8D7h |

A PSP's CALL 5 (a far call to F01D:FEF0h, for example) reaches 0:00C0h (INT_DOSCALL5) only by wrapping around at 1Mb, so with A20 enabled, it lands at 1000C0h instead; like DOS 5 with DOS=HIGH, CPU$ puts a far jump to 0:00C0h there.  In protected mode, a real-mode segment isn't a selector, so a PSP's PSP_FCSEG is SEL_CALL5 instead (see psp_setmem), a call gate to SEL_C5CODE:00C0h, the far jump that sysinit stores at 0:00C0h (see set_call5); a far call through a gate ignores its offset, so PSP_SIZE keeps the value that CP/M programs read as their memory size.

The GDT's limit extends through the last identity selector (F800h), so the descriptors between its first 256 entries and A000h overlap the rest of the system area; CPU$ clears the whole area first, so most of them (everything from 88E0h up, other than the identity selectors; the TSS's few non-zero bytes never form a present descriptor) aren't present, and loading one of those selectors (eg, a real-mode segment by mistake) faults.

Before writing to the system area, CPU$ checks that A20 really is enabled (that SYSVARS isn't aliased to 0:0000h), and on every function call, it checks the SYSVARS signature and re-enables A20 if necessary (eg, if a program used the BIOS block move function, INT 15h function 87h, which turns A20 off).

Selectors 70h-7F8h (GDT) and 04h-2FCh (the active session's LDT) are allocated by CPU_ALLOC, CPU_MAP, and CPU_ALIAS (and CPU_PMODE); a descriptor whose access byte is zero is free.  On the baseline 2Mb PC AT, for example, devinit's code selector is 70h, and each driver gets a data selector and a code selector after that (eg, 80h and 88h for CPU$, and 90h and 98h for NUL; see [Protected-Mode Initialization](#pminit)).  All descriptors are 80286-format (the 80386 fields are zero, except bits 31-24 of the base, for blocks above 16Mb) and DPL 0 (unless MEMF_USER is set).

### Physical Memory Arena {#arena}

The 80286 driver's arena is a table of Physical Memory Blocks (PMBs) in address order, covering all memory from 0 to the end of extended memory, with the last PMB marked PMBSIG_LAST ('Z'), like the last MCB:

| Field | Size | Contents |
|-------|------|----------|
| PMB_SIG | byte | 'M', or 'Z' for the last PMB |
| PMB_TYPE | byte | PMBTYPE_* |
| PMB_OWNER | word | Owner (from CPU_ALLOC's BX), or zero |
| PMB_ADDR | dword | Physical address |
| PMB_LEN | dword | Length, in bytes |
| PMB_SEL | word | First selector (if any) |
| PMB_NSEL | word | Number of selectors |
| PMB_MCBTYPE | byte | Block type (MCBTYPE_*, as in an MCB), or zero |
| (reserved) | byte | |
| PMB_CODE | word | The block's code alias (see [Code Aliases](#aliases)), or zero |
| PMB_LDT | word | The LDT that was active when the owner was set (see CPU_FREEALL) |
| (reserved) | 2 bytes | |
| PMB_NAME | 8 bytes | Name of the process (as in an MCB), or zero |

CPU_ALLOC uses the first free block that's big enough, anywhere in memory (splitting it if necessary), unless MEMF_LOW, MEMF_HIGH, or MEMF_AT says otherwise, CPU_REALLOC shrinks a block or grows it into the free block after it, and CPU_FREE frees the block's selectors and merges it with any free neighbors.

Unlike MCBs, PMBs aren't stored in front of the memory they describe:

- the arena has to describe memory that isn't RAM (eg, 640K-1Mb), where no header could be stored;
- headers in extended memory couldn't be read or written in real mode, which is where CPU$ is called from until the kernel runs in protected mode;
- blocks need no header, so they stay aligned, and a block can be mapped by a selector with no offset; and
- a program that writes past the end of its block can't damage the arena.

The cost is a fixed number of PMBs (128 for now; a CONFIG.SYS option could change it).  The 8086 driver's arena is the MCB chain itself: programs on an 8086 expect to see MCBs, and conventional memory is all there is.

For debuggers that can't call CPU$ (eg, the PCjs Debugger), whichever driver stays stores the real-mode address of its arena in CPU_ARENA (0:514h): the 8086 driver's first MCB, or the 80286 driver's PMB table (FFFF:08E0h, the only arena above 1Mb).  The PCjs Debugger's `d dos` command uses it to list the arena the way DEBUG's DM does, in either mode, with each of the system's blocks shown as the drivers in it (from DD_LIST, whose links are selectors in protected mode); it labels the memory DOS is in by DOS's INT 20h handler, since it can't call DOS_MSC_GETVARS, so until sysinit installs that, the kernel's block shows as SYS.

#### Claiming Memory at Boot {#claiming}

Once CPU$ has initialized, everything that runs during the boot declares the memory it uses, with either driver and in either mode, and moves memory with CPU$ rather than on its own:

1. **devinit** (`chk_cpu`, before the first driver after CPU$ loads) claims two blocks with CPU_ALLOC and MEMF_AT: the drivers that haven't initialized yet, and its own code, CONFIG.SYS data, and scratch buffer.  Then, while it's still in real mode (so that it can use the boot code's `read_file`), it allocates a block for BASDOS.COM at the top of conventional memory (MEMF_LOW + MEMF_HIGH), loads BASDOS.COM into it, and copies the CONFIG.SYS data after it.
2. **Each driver** that shrinks (or grows) during its initialization has the drivers after it moved with CPU_MOVE.  The one exception is the first move on an 8086 (or with `CPU=8088`), where the 80286 CPU$ unloads itself before any CPU$ is loaded, so devinit moves the drivers after it down itself; reclaiming the memory of a driver that doesn't stay is devinit's job, not CPU$'s.
3. **When the last driver is done** (`i9`), devinit shrinks the drivers' block to fit (CPU_REALLOC), frees its own block and BASDOS.COM's, and allocates BASDOS.COM's new home with CPU_ALLOC and MEMF_LOW, which is the first free block, right after the drivers (and their MCB, with the 8086 driver); the block reaches at least the end of devinit, because the 8086 driver puts a free MCB after it, which must not land on devinit's code or data before the move (sysinit resizes the block anyway).  Then it pushes sysinit's inputs (including BASDOS.COM's new address) and its new entry point, and jumps to CPU_MOVE, which moves BASDOS.COM (over devinit) and "returns" to sysinit.
4. **sysinit** (with `move_init`, `dos_size`, `init_free`, and `map_buf`, in drvinit.asm) allocates a block at the top of conventional memory for its initialization code, CONFIG.SYS data, and a 512-byte stack below them, moves them there with CPU_MOVE, and jumps to them through a data selector and code alias for the block (CPU_MAP and CPU_ALIAS).  It grows the kernel's block as much as it can (CPU_REALLOC returns the longest a block could be), builds its tables after the kernel at offsets in the kernel's segment (`init_table`), gets a segment (or selector) for each disk buffer from CPU_MAP, and shrinks the block to fit.  Before loading the SHELLs, it gives back the part of its block below `sysinit_tail` (by freeing the block and claiming the rest again), which is everything except its stack and systail.asm (linked last: the SHELL loop and only the code, data, and CONFIG.SYS data it needs), and when they're loaded, it frees the rest.

Once CPU$ is loaded, neither devinit nor sysinit computes a segment from an address, or relocates memory itself.  Before then, devinit calls the first driver (CPU$) at its fixed segment (BIOS_END), and moves the drivers itself if the 80286 CPU$ unloads (above); and sysinit sets DOS's memory limit (`mcb_limit`, for PSP_PARAS) from the BIOS's MEMORY_SIZE.  (They do still copy the CONFIG.SYS data, into blocks that CPU$ gave them.)

After the boot, the kernel's memory functions (memory.asm) are just calls to CPU$, with the block's segment (or selector) in CX and DX = -1: DOS_MEM_ALLOC calls CPU_ALLOC (without MEMF_LOW, so a block can be anywhere in memory, including extended memory in protected mode, plus MEMF_HIGH for MCBTYPE_HIGH) and CPU_SETBLK (the owner and type), DOS_MEM_FREE calls CPU_FREE, DOS_MEM_REALLOC calls CPU_REALLOC, loading a program names its block with CPU_SETBLK, a program's blocks are freed with CPU_FREEALL when it ends, and DOS_UTL_QRYMEM (for MEM), finding a loaded copy of a program's code, and DEBUG's DM use CPU_QUERY.  There's no MCB chain for programs to walk, other than the 8086 driver's, so DOS_MSC_GETVARS's `mcb_head` is zero; MEM's total memory is DV_MEM_SIZE (which DOS_MSC_GETVARS returns in AX), which sysinit sets to the conventional memory (MEMORY_SIZE) plus every block that CPU$ describes above 1Mb (`mem_total`), so on the baseline PC AT in protected mode, MEM reports all 2Mb.

### Switching Modes

CPU$'s `pm_call` runs a function in protected mode and returns to real mode, with interrupts and NMI disabled.  It points SEL_STACK at the caller's stack, saves SS:SP, loads the GDTR and IDTR, sets PE with LMSW, jumps to SEL_CPUCODE, and loads DS, ES, and SS with SEL_SYS and SEL_STACK, and LDTR with SEL_LDTD.

An 80386 returns to real mode by clearing PE (`MOV CR0,EAX`, assembled as bytes, since MASM 4.00 knows only 80286 instructions).  An 80286 can't, so before switching, `pm_call` sets the CMOS shutdown code (CMOS register 0Fh) to 0Ah and stores the address of `pm_resume` in 40:67h, and to return, it pulses the 8042's reset line (command FEh), as the BIOS's own block move (INT 15h function 87h) does.  After the reset, the BIOS sees the shutdown code and jumps through 40:67h without initializing anything else (both the original 1984 PC AT BIOS and the 1985 revision 3 support shutdown code 0Ah), and `pm_resume` restores SS:SP and the real-mode IDTR, clears the shutdown code (so that a later CTRL-ALT-DEL does a normal POST), and enables NMI again.  Because the shutdown code is set before switching, a "triple fault" (which resets the processor) also returns to `pm_resume`, and every IDT entry points to a fault handler that returns to real mode, too, so a bug in protected mode makes the caller's test fail instead of hanging the machine.

The CPU$ self-test (`pm_test`) checks that PE is set and writes and reads back a word at 110000h (through SEL_TMP), which real mode can't reach; CPU$ stays loaded only if that works.

CPU_PMODE (below) switches to protected mode the same way, but for good: it never returns to real mode.

### Protected-Mode Interrupts {#interrupts}

After CPU_PMODE, every interrupt goes through the protected-mode IDT (SYS_PIDT), and the master PIC is moved from 08h to 78h, next to the slave PIC (70h-77h), so that IRQs 0-7 no longer share vectors with processor exceptions.  Its default gates "reflect" each interrupt to the handler in the real-mode vector table, if that's in the ROM (whose segments are identity code selectors, eg, F000h), at ring 0:

| IDT entries | Default gate | Reflected to |
|-------------|--------------|--------------|
| 00h | `exc_stubs` (DPL 3) | Divide errors (DPL 3, since ring 3 code may issue INT 0, as FPU$ does, and an INT 0's frame is the same as a divide error's) |
| 01h-02h, 06h-0Fh | `exc_stubs` (DPL 0) | Exceptions: fatal, except the cases below |
| 03h-05h, 10h-6Fh, 80h-FFh | `sw_int` (DPL 3) | Software interrupts: the vector's handler, if it's in the ROM; otherwise fatal |
| 70h-77h | `irq_stubs` (DPL 0) | IRQs 8-15: vectors 70h-77h's handlers, if in the ROM; otherwise an EOI |
| 78h-7Fh | `irq_stubs` (DPL 0) | IRQs 0-7: vectors 08h-0Fh's handlers, if in the ROM; otherwise an EOI |

- **Reflection**: `irq_common` "returns" to the ROM handler with the interrupt's own frame on the stack, so the handler returns straight to the interrupted code.  `sw_int` gets the vector from the caller's `INT n` (or `INT3`) instruction, and calls the handler with interrupts disabled and a frame that returns to `si_ret`, which copies the handler's result flags (CF, ZF, SF, and OF) to the caller's.  Everything runs at ring 0, on the caller's stack, or for an interrupt from ring 3, on the TSS's ring 0 stack (see [Running Programs at Ring 3](#ring3)).
- **Drivers' handlers**: in protected mode, DDINT_GETVEC and DDINT_SETVEC go to CPU$'s `pm_getvec` and `pm_setvec`, which read and write the IDT, not the real-mode vector table: setting a vector replaces its gate's selector and offset (for vectors 08h-0Fh, the gates for IRQs 0-7, at 78h-7Fh), keeping the gate's DPL (above), so the driver's handler is called directly, and getting a vector returns its gate, or if the gate is a default one, its real-mode vector if that's in the ROM (eg, F000:FEA5h for INT 08h, which CLOCK$ chains to), or 0:0 if not.
- **INT 13h**: CPU$ reflects INT 13h like any other BIOS call, and FDC$, which makes every disk transfer (HDC$ reads MBRs through FDCX_MBR), works around the BIOS's real-mode assumptions about ES:BX in `pm_rw` (which in real mode is part of FDC$'s sector buffer instead).  The diskette BIOS turns ES:BX into a DMA address (ES * 16 + BX), so ES:BX becomes BIOS (SEL_BIOS, whose base is 400h) and the buffer's offset from 400h; a buffer more than 64K above 400h goes through FDC$'s sector buffer, a sector at a time, since `readwrite_sectors` gets each buffer's address from CPU_SEGINFO (`pm_dma`) for its 64K DMA boundary check.  The AT fixed disk BIOS uses programmed I/O, but it normalizes ES:BX by adding BX / 16 to ES, which makes ES an invalid selector unless BX is less than 16, so the buffer gets a selector of its own (CPU_MAP) with a zero offset.  FDC$'s other real-mode assumptions are gone, too: `readwrite_sectors` advances the transfer address between tracks by adding to the offset, not ES (DOS's buffers never extend beyond offset FFFFh), and `set_dpt` updates the DPT at DPT_ACTIVE (40:122h), where the boot code puts it, rather than through the INT 1Eh vector, which DDINT_GETVEC can't return in protected mode.
- **Vectors 08h-0Fh** are also software interrupts sometimes (eg, the AT BIOS's IRQ 9 handler does `INT 0Ah`), so if an exception's frame (taken as having no error code) returns just past an `INT` for its vector, `exc_common` treats it as one.
- **Null selectors in the ROM**: the BIOS loads DS with 0 to address the vectors (eg, the AT BIOS's GET_PARM does `LDS SI,[78h]` with DS = 0), so a general protection fault with a zero error code, in the ROM, while DS or ES holds a null selector, is retried with SEL_LOW (base 0).  BASIC-DOS's own code gets no such fix.
- **Anything else** (any other exception, an INT 3, such as a failed DEBUG assertion, or a software interrupt with no handler we can call) goes to the fault handler (see CPU_SETFAULT), which is the kernel's `dos_fault` unless a debugger has replaced it: if the exception occurred in the current program's own code (its PSP_START segment, or any block that the program owns, such as one of COMMAND's code blocks, which CPU_QUERY finds from the selector), DOS displays `CPU fault vv (EC=xxxx) at cccc:iiii` and ends the program with exit code 255 and EXTYPE_FAULT, as it does for a divide error, and the system continues; otherwise (eg, in the kernel, a driver, or the ROM), `dos_fault` declines it (by returning), and the exception is fatal: `cpu_fatal` prints, with the BIOS, the same `CPU fault vv (EC=xxxx) at cccc:iiii` line, where EC is the error code (for a software interrupt, the caller's AX), followed by `System halted`, offers the halt to the fault handler (with FAULT_HALTED; see CPU_SETFAULT), and unless a debugger takes it, stops the machine.  An exception in CPU$ or in the kernel itself never reaches the kernel's handler (CPU$ skips the handler's own code, for the offer, too).  DEBUG.COM passes each exception on to `dos_fault` unless its VT command traps the vector, and GT passes on a trapped one; either way, if `dos_fault` declines it, DEBUG.COM stops at the faulting instruction first, as if the vector were trapped, so that G can retry it (eg, after a fix), and GT then returns it to CPU$, which reports it and offers DEBUG.COM the halt: DEBUG.COM keeps control, displaying the same `CPU fault` and `System halted` lines, and waits for CTRL-C (or BREAK) before displaying the registers and its prompt; G, P, and T then resume at CS:IP (eg, after a fix), and GT keeps the machine halted (displaying the messages and waiting again), so that DEBUG.COM never gives up control.

### Protected-Mode Initialization {#pminit}

On an 80286 or later, when CPU$ stays loaded, BASIC-DOS switches to protected mode during devinit, right after CPU$ initializes, and never switches back; everywhere else (an 8088, or `CPU=8088`), nothing changes, and the same code runs in real mode:

1. **CPU$ initializes in real mode**, as the first driver.
2. **devinit claims its memory and loads BASDOS.COM** (`chk_cpu`), as it does in real mode (see [Claiming Memory at Boot](#claiming)).
3. **devinit calls CPU_PMODE**, which turns its CS into a code selector, DS, ES, and SS (all 0) into SEL_LOW, the view of the first 64K that devinit uses to reach the drivers, points DDINT_CPU, DDINT_GETVEC, and DDINT_SETVEC at CPU$'s protected-mode code, moves the master PIC, and loads the protected-mode IDT.  devinit then gives the drivers already in the chain (ie, CPU$) selectors, too.  The 80286 driver stays only if it can switch to protected mode, so if CPU_PMODE fails, devinit halts.
4. **Each driver gets a code selector and a data selector** before its initialization, unless it's skipped (`get_sels`, which calls CPU_MAP for a 64K data selector and CPU_ALIAS for its code alias; in real mode, both are the driver's segment): devinit stores the data selector in DDH_DATA and DDPI_END, calls the driver through its code selector, and links it into the chain (DDH_NEXT_SEG, FDC_DEVICE, HDC_SEG, and CLOCK_DEVICE) with its code selector.  When the driver's initialization returns, devinit fits both selectors to the length the driver keeps, with CPU_SETLIM (`fit_sels`), so that they end where its resident code and data do, or frees them with CPU_UNMAP if it keeps nothing; CPU$'s own selectors (from step 3) are fitted the same way.  The selectors are 64K until then, since a driver can keep more than its file (eg, FDC$'s sector buffer overlays its initialization code and extends past it).  devinit also passes its own data selector in DDP_PTR and DDPI_BUFPTR.  Every built-in driver (NUL, VKD$, COM1-COM4, LPT1-LPT3, CLOCK$, FDC$, HDC$, PIPE$, FPU$, and MOUSE$) initializes this way, and VKD$, COM, and CLOCK$ install their interrupt handlers in the IDT with DDINT_SETVEC (see [Protected-Mode Interrupts](#interrupts)).
5. **devinit moves BASDOS.COM after the drivers and jumps to sysinit** (`i9`), as it does in real mode: it gets a code selector and a data selector for BASDOS.COM's new home, pushes the offset of the BPB (in the first 64K), the size of the CONFIG.SYS data, the data selector, and the CONFIG.SYS data's offset, which sysinit pops, and then CPU_MOVE "returns" to its entry point (CS:0002h).
6. **sysinit runs in protected mode**: it moves its initialization code to the top of conventional memory (see [Claiming Memory at Boot](#claiming)), jumps there through a data selector and code alias for the new block (CPU_MAP and CPU_ALIAS), and uses the data selector as SS; `dos_seg` is the kernel's data selector (from devinit), not CS.  It points the DOS vectors (in CPU$'s IDT) and DDINT_UTIL at the kernel's code selector (`dos_code`, the CS that sysinit is entered with), and `set_call5` stores the CALL 5 jump at 0:00C0h through a selector for the first 64K from CPU_MAP, which it then frees (CPU_UNMAP); DDINT_GETVEC and DDINT_SETVEC are CPU$'s, so sysinit leaves them alone.  It builds its tables (the SCBs, BPBs, and SFBs) at offsets after the kernel (`init_table`), gets a segment (or selector) for each disk buffer (including the two in low memory) from CPU_MAP, which is what the buffer chain links, opens its devices, loads any DEVICE= drivers (`load_devices` calls each driver's INIT through the code alias of its block, and links the driver with it), hooks INT 21h for its SHELL cache, loads the SHELLs (DOSUTIL LOAD), and points DDINT_ENTER and DDINT_LEAVE at the kernel.
7. **The first session starts**: `dos_leave`'s IRET starts it, with CS set to the code alias of its program's block (see [Code Aliases](#aliases)), and COMMAND.COM initializes and runs commands and BASIC programs in protected mode.  DEBUG.COM, loaded as a driver, gets any fault after it's loaded (see CPU_SETFAULT), and with /H (eg, `DEVICE=EXT\DEBUG.COM COM2:9600,N,8,1,VT100 /H`), it also stops as soon as it's loaded.

#### The Protected Mode Demo {#pmdemo}

The [Protected Mode demo](/demos/mmu/), a 2Mb PC AT with a Color Display and a DEC VT100 on COM2 for DEBUG.COM, boots the BASIC-DOS Protected Mode Demo diskette, whose CONFIG.SYS has no `CPU=8088` line.  DEBUG builds refresh that diskette, so that it has the assertions.  The demo's [Debugger](/demos/mmu/debugger/) page is the same machine with the PCjs Debugger.

When the boot sector's `Press a key to start...` prompt times out (pressing **Esc** at the prompt boots the hard disk instead, whose CONFIG.SYS has `CPU=8088`), CPU$ initializes and switches to protected mode, and everything after that runs in protected mode: the rest of the drivers, the kernel's initialization (sysinit), the diskette's CONFIG.SYS driver, DEBUG.COM, on COM2 (which prints its banner on the VT100), and COMMAND.COM, which loads from the hard disk (so C: is the default drive, and PATH$ lists C:'s directories), and whose prompt appears on the Color Display.  Commands, BASIC programs, and NE programs work (eg, `PRIMES` in `C:\TESTS\MISC`, which runs PRIMES.EXE there), but MZ EXE files can't run in protected mode, so COMMAND reports "Unable to load X" for them (see [Code Aliases](#aliases)).  CPU$ gives each fault to DEBUG.COM, and the VT100 shows the fault (eg, `CPU fault 0D`) with its error code, and the registers at the faulting instruction (with `#` before its address, since it's in protected mode, and the name of the memory it's in after it).  Adding /H to the DEBUG.COM line in CONFIG.SYS stops it as soon as it's loaded, so that you can set breakpoints before booting continues.  The B: drive has the BASIC-DOS Tests diskette, so `B:\TESTS\MISC\CPUTEST` prints CPU$'s memory arena and tests its functions, and `B:\TESTS\MISC\FAULT n` causes exception *n* (0, 1, 3-6, 12, or 13; eg, `FAULT 13` writes to CS, a general protection fault), or with -1, a fatal fault in the kernel (by passing DOS a null pointer to a filename), to see how BASIC-DOS responds: DOS reports a divide error (0) or an overflow (4) and ends the program, a single-step trap (1) or a breakpoint (3) resumes (unless DEBUG.COM stops there), and DOS ends the program for the rest (eg, `CPU fault 0D`), unless DEBUG.COM's VT command traps the vector (eg, `VT 0D` or `VT 13.`), which stops the machine at the faulting instruction, after which GT passes the fault on to DOS.  A fault that DOS can't handle (outside the program's own code) stops DEBUG.COM, too, whether or not VT traps it, before CPU$ prints `System halted` and stops the machine.

#### Debugging {#pmdebug}

- In the PCjs Debugger, `r` shows each segment register's selector with its base and limit in protected mode (eg, `CS=0018[000970,FFFF]` in CPU$), along with the GDTR, IDTR, LDTR, and TR.
- Linear breakpoints (eg, `bp %1295`) work in either mode.  An address in CPU$ is 970h plus its offset in 286DEV.MAP (eg, `cpu_fatal`, which reports a fatal exception and stops the machine).
- `tools/tests/pmboot.sh` boots in protected mode on the baseline 2Mb PC AT (with the console on COM1), and lists breakpoint addresses for the PCjs Debugger: CPU$'s, along with `dv_init` (in devinit, just before each driver's initialization) and `dv_jump` (just before sysinit).
- `d dos` lists CPU$'s memory arena the way DEBUG's DM command does, in either mode, once CPU$ has initialized: each block's address, length, owner, and name or type, with the system's blocks shown as the drivers in them (eg, CPU$ at 000970h; see [Physical Memory Arena](#arena)).
- Clear a breakpoint (`bc *`) before tracing (`t`) from it, or the trace stops there again.
- To stop as CPU$ starts to initialize, halt the machine, set `bw %976 'if cs==97;h;else'`, and reset: it's a write breakpoint on CPU$'s DDH_REQUEST field (CPU$ is the first driver, at 0097:0000), which halts only when CPU$ itself writes it, as the start of its initialization does, so it doesn't depend on how CPU$ is built.
- To have the PCjs Debugger, rather than DEBUG.COM, stop at a DBGBRK (a lone INT 3) or an assertion failure, turn on its INT and HALT messages (`m int on` and `m halt on`) before booting (without the write breakpoint above, since with HALT messages on, it also stops the machine where it shouldn't).
- BASIC-DOS's own debugger, DEBUG.COM (on the demo's VT100), works in either mode (as a driver or a program): an address can start with `&` (real mode) or `#` (protected mode), and otherwise has the processor's current mode, or with `%`, it's a physical address (eg, `%100000`), `DS selector` displays a selector's descriptor as the PCjs Debugger's DS command does (eg, `base=000970 limit=FFFF type=1B (code,readable,accessed) ext=0000 dpl=00`), `R` also shows the MSW, GDTR, and IDTR, and in protected mode, uses the PCjs Debugger's format (each segment register's base and limit, A20, the LDTR, GDTR, IDTR, TR, MSW, and the flags as 0 or 1), and `LN [address]` ("list near") shows an address (CS:IP by default), its linear address, and the name of the memory it's in (eg, `#0128:3754 0095E4 <DOS>`), as DM would show it.

### Running BASIC-DOS in Protected Mode {#plan}

Staying in protected mode after CPU$ initializes is the goal, but the rest of BASIC-DOS assumes real mode in several ways, and each needs its own solution.  This design targets the PC AT (an 80286, with IBM's BIOS); the 80386 (eg, virtual-8086 mode for DOS programs) and other BIOSes, such as the DeskPro 386's, are for later.

1. **BIOS calls** (*done*, for what the drivers' initializations use).  The ROM BIOS runs at ring 0 in protected mode, with identity selectors, a fix for null selectors, and reflection through the real-mode vector table (see [Protected-Mode Interrupts](#interrupts)), so a BIOS call needn't cost a mode switch, which on an 80286 means a processor reset (as in OS/2 1.x's real-mode session).  The rest of the BIOS functions the drivers use still need trying, diskette (DMA) buffers more than 64K above 400h could use an identity selector (rather than FDC$'s sector buffer), and a few functions (eg, INT 15h functions 87h and 89h) will need CPU$ replacements.
2. **Hardware interrupts**.  The master PIC's IRQs 0-7 use vectors 08h-0Fh, which are also processor exceptions (eg, 0Dh is a general protection fault).  CPU$ moves the master PIC to 78h-7Fh, next to the slave PIC (70h-77h), and reflects each IRQ to the BIOS's handler, unless a driver has installed its own handler (eg, CLOCK$'s timer handler), which is called directly (*done*; see [Protected-Mode Interrupts](#interrupts)).  Vectors 08h-0Fh can still be software interrupts (eg, INT 0Ah from a BIOS's IRQ 9 handler), so their gates tell the two apart.
3. **Segment arithmetic**.  The kernel and COMMAND.COM compute segments from paragraphs (eg, walking the MCB chain, `mov ax,es` + `inc ax` to get from an MCB to its block, PSP and environment segments, and paragraph rounding), use fixed segments (0 for low memory, 40h, B000h and B800h for video, and F000h for the ROM), and use `push cs` + `pop ds` and then write data (a code segment can't be written in protected mode).  Each case needs a selector: for example, DOS_MEM_ALLOC could return a selector from CPU_MAP for the new block (keeping the MCB in the arena below 640K), the fixed segments would become fixed selectors (SEL_LOW, plus SEL_VIDEO and SEL_ROM), and each module with a code segment would also get a data alias (eg, the next selector).  The first step is an inventory of every such case.
4. **DOS programs**.  COM and EXE programs are real-mode programs.  On an 80386 they can run in virtual-8086 mode; on an 80286, only in real mode, so a session running a DOS program would switch the processor back to real mode while it runs (much like OS/2's DOS session), and other sessions would wait.
5. **COMMAND.COM**.  The biggest payoff: BASIC programs, variables, strings, and arrays limited only by memory, with each block in extended memory and addressed by a selector.

#### Mode-Independent Code {#modeless}

The first step toward staying in protected mode is to change the drivers and the kernel (everything that will run at ring 0) so that the same code runs in either mode, by using only segment values that are also valid selectors, and by never writing to a code segment.  The rules, *in progress*:

1. **Low memory through segment 40h** (*done*): bios.inc's BIOS segment is now `at 40h`, as the ROM BIOS itself addresses its data, instead of 0, and it covers both the ROM BIOS data area (offsets 00h-FFh) and BASIC-DOS's low memory (500h-96Fh, at offsets 100h-56Fh): CPU_TYPE, the DDINT entry points, the DPT, and the two disk buffers.  In protected mode, 40h is an identity selector.  BIOS_DATA (400h) is the segment's linear address, for the few places that need a linear address (eg, the two disk buffers' addresses, for CPU_MAP, and devinit, which addresses the drivers through segment 0).
2. **Interrupt vectors through DDINT entry points** (*done*): segment 0 is the null selector, and the general protection fault fix for it should only ever be needed by the ROM BIOS, so drivers and the kernel read and write vectors with far calls to DDINT_GETVEC and DDINT_SETVEC (after DDINT_CPU), which pass vectors in DX:CX rather than in segment registers (see [Device Drivers](../dev/)).  CPU$ provides them, since one CPU$ always stays, and it initializes first, so they're ready for every other driver's INIT, before the kernel is loaded: the 8086 driver's use the vector table, and the 80286 driver's, from CPU_PMODE on, use its IDT.  Only the boot code and devinit, which run first, and sysinit's CALL 5 jump at 0:00C0h (code, not a vector) still use segment 0, along with HDC$'s MBR code (which runs at boot), CPU$'s A20 test, and the 8086 CPU$'s vector functions (which run only in real mode).  COMMAND.COM no longer reads the INT 33h vector to find a mouse driver (see [COMMAND.COM](#command)).
3. **DDINT entry points through segment 50h** (*done*): drivers and the kernel call the DDINT entry points through segment 50h (eg, `call far ptr DDINT_SETVEC` is CALL 0050:003Ah), which in protected mode is SEL_DDINT, a code selector with the same base (500h), so the addresses are the same in either mode; 40h stays a data selector.  The slots are still written through segment 40h (bios.inc's DDINT segment is at 50h, and an operand like `ds:[DDINT_CPU]`, with DS assumed to be BIOS, gets the BIOS offset from LINK, while an immediate offset needs DDINT_BIAS added).  In protected mode, CPU$ points DDINT_CPU, DDINT_GETVEC, and DDINT_SETVEC at its own protected-mode code (see [Protected-Mode Initialization](#pminit)).
4. **No writes through CS** (*in progress*): a protected-mode code segment can't be written, so each write with a CS override became a write through DS, ES, or SS holding the module's own segment (eg, after `push cs` and `pop ds`), in the drivers, the kernel, COMMAND.COM, DEBUG.COM, and the tests (FCBTESTS, DOSTESTS, CPUTEST, HARDERR, and IOERR; see [Code Aliases](#aliases)).  In the kernel, those segments now come from `dos_data` (eg, `mov ds,cs:[dos_data]`), where sysinit stores the kernel's data segment (or selector), and sysinit's relocated code uses SS, its own data selector (or `init_data`, in `cache_int21`, which runs on its caller's stack); `sprintf` still loads DS from CS, since it only reads through it (and it's also part of PRINTF.COM).  A write through SS needs no change at all.  MASM also gives a write an implicit CS override when the segment register that would otherwise address the variable is assumed to be NOTHING; a scan of the kernel's binary for CS-prefixed writes found one (LOCK_SCB in `mcb_getsize`), which now goes through ES, but the drivers, COMMAND.COM, and DEBUG.COM haven't been scanned yet.  Writes to a driver's own memory now go through its data selector (see the next item).
5. **No unnecessary null selectors**: segment registers are never loaded with 0 just to have a value (three places in the kernel did, before read_buffer replaced it anyway), since only the ROM BIOS should ever need the null-selector fixup.  An empty chain's far pointer (eg, CLOCK$'s list of waiting packets) has an offset of FFFFh and a segment of 0, rather than -1:-1, so that loading the whole pointer before checking the offset is safe (see [Device Drivers](../dev/)), and sprintf treats a null string pointer (eg, an empty BASIC string, for WRITE's `%.*ls`) as an empty string, rather than reading 0:0.
6. **A data selector for every driver** (*done*): DDH_INTERRUPT (unused, except by COM, which now keeps its interrupt entry with its other per-port variables) is now DDH_DATA, the driver's data segment or selector, which devinit (or the kernel, for DEVICE= drivers) stores in the header before calling the driver's initialization, so every entry point (requests, interrupt handlers, and the far entry points that FDC$ provides HDC$) can load it with `mov ds,cs:[0].DDH_DATA` (instead of `push cs` and `pop ds`) whenever it writes its own memory.  In real mode, it's the driver's segment, so nothing changes; in protected mode, the driver's code selector (CS) and data selector are separate selectors for the same memory, from CPU$.  Far pointers to a driver's code (eg, vectors, DDH_NEXT_SEG, FDC_DEVICE, and BPB_DEVICE) use its code selector, and pointers to its data (eg, FDC$'s ddbuf_ptr) use its data selector.
7. **A new program's FLAGS** (*done*): FL_DEFAULT is 0202h, not F202h (as an 8086 pushes FLAGS), since at ring 0 in protected mode, an IRET with F202h sets IOPL 3 and NT, and the next IRET with NT set (eg, the kernel's, after a CALL 5, which unlike an INT doesn't clear NT) is a task switch through the TSS.

The boot sector, which runs at 0:7C00h and then 0:0560h before anything else, keeps using segment 0 (adding BIOS_DATA to every BIOS offset), as does devinit to reach the drivers (through SEL_LOW, in protected mode), although it relocates them with CPU_MOVE.

DEBUG builds also report (and halt on) the first failed assertion, even before any console handle exists: the kernel installs a default INT 29h handler (BIOS output) whenever no driver has (eg, VKD$ isn't loaded), so the fallback in write_handle never calls a null vector.

#### COMMAND.COM {#command}

COMMAND.COM will run at ring 3, so beyond the rules above, it should use only selectors that the kernel gives it.  *Done*:

- **Which copy owns the shared code**: it used to compare CS with DS (or SS), which are different selectors in protected mode even for the owner; now it checks PSP_HEAP, since only another copy's heap starts right after its PSP (see load_program).
- **The environment**: it used to be a paragraph-aligned buffer in the heap, whose segment was DS plus a paragraph offset; now it's a block of its own, allocated from the top of memory while COMMAND runs a program (and freed when it ends), so that it never sits after COMMAND's block (where it would keep the transient portion's memory from being reused).
- **The transient portion's copy**: it used to be placed at the top of the highest free block, computed from that block's segment and size; now COMMAND allocates a block there, copies the transient portion into it, and frees it again (it's still checksummed before it's reused).
- **Graphics memory**: the graphics statements used B800h; now they ask VKD$ (IOCTL_GETMODE with CL = 1 returns the context's video memory in DX, which in protected mode will be a selector) and cache it with the mode.
- **Fixed segments and vectors**: the tick count for RANDOMIZE uses segment 40h, and MOUSE no longer reads the INT 33h vector (it checks whether MOUSE ON found a mouse, and MOUSE ON resets the mouse with INT 33h, which is always valid, since sysinit points it at an IRET when there's no mouse driver).
- **Generated code** (see [Code Aliases](#aliases)): COMMAND compiles BASIC into code blocks (CBLKs, and FBLKs for user-defined functions) that it allocates as data, runs them, and patches them while they run (genMore replaces each placeholder, which it finds from its return address).  Each block's code alias is what code transfers into (`codeSeg`), and everything else (the block chains, labels, code generation, and patching) uses the block's data selector.  Generated code that writes to its own block (eg, an FPU$ function storing a result in a double's 8-byte slot, which genSlot reserves in the block) gets the block's data segment (or selector) from CBLK_DATA (`MOV ES,CS:[CBLK_DATA]`, or `PUSH CS:[CBLK_DATA]` for a slot passed as a parameter; see genBlkData), rather than from CS.
- **The shared code's variables**: CMD_REFS, TRANS_SUM, TRANS_HI, CMD_PATH (and MSG_DRIVE), and FPU_TABLE are in COMMAND's code segment, and every copy now writes them through CODE_DS, the owner's data segment (or selector), which the owner stores at startup.
- **The transient portion's copy**: a freed block's selector isn't valid in protected mode, so instead of keeping the segment of the block it copied the transient portion into (and freed), COMMAND allocates the same size at the top of free memory again when the program ends, which is the same memory unless something else has allocated it, and checks the copy's checksum as before (see DOS_UTL_QRYMEM in [Utility Functions](../util/#memory)).
- **Freed selectors on the stack**: freeAllBlocks preserved the caller's ES, so freeing the block that ES held (eg, the code blocks, when a program ends) reloaded a freed selector; now it returns ES = 0 in that case, as DOS_MEM_FREE does, and so does compactStrs; genCode sets ES to the heap before freeing a program's code (ES may hold a code block's alias); and findErl (for ERL) looks for a return address in a code block by comparing each word on the stack with the blocks' code segments, rather than loading it into ES.

- **DEF SEG, PEEK, and POKE**: a DEF SEG segment is mapped to a selector, read-only except for video memory (see [DEF SEG](#defseg)).

*Remaining*:

- **A read-only code segment**: the shared code's variables could move out of the code segment (eg, the share count into the kernel, which already finds the matching copy, and the rest into each copy's heap), so that the code segment would be read-only: one execute/read selector that every copy shares, with no checksums (nothing could modify it) and, with extended memory, perhaps no transient portion at all.  The hard part is establishing that separation, since today the shared code is simply the first part of the owner's COM image.

#### Code Aliases {#aliases}

A protected-mode segment is either code (executable, and at most readable) or data (readable, and perhaps writable), so memory that's both written and executed needs two selectors.  CPU_ALIAS (tested by CPUTEST) creates the second one: given a selector from CPU_ALLOC, CPU_MAP, or CPU_ALIAS, it returns a new selector for the same base and limit, with the access rights selected by MEMF_CODE, MEMF_RDONLY, and MEMF_USER; CPU_UNMAP frees it.

A block's own code alias (CPU_ALIAS with just MEMF_CODE, for the selector that CPU_ALLOC returned for the block) is special: the 80286 driver creates it only the first time, keeps it in the block's PMB (PMB_CODE), returns the same selector every time after that, and frees it with the block (and when CPU_REALLOC shrinks a block, the alias stays with the block, not the freed end).  So nothing else has to keep track of the pair, and it must never be freed with CPU_UNMAP.  The kernel returns it for any memory block with DOS_UTL_ALIAS (27h; see [Utility Functions](../util/#memory)), since ring 3 code won't be able to call DDINT_CPU; in real mode, a block's code alias is its segment.

- **COMMAND.COM's code blocks** (*done*): allocBlockMin gets each CBLK's and FBLK's code alias when it allocates the block (freeing the block if it can't), so getting it later can't fail, and `codeSeg` returns it wherever code transfers into a block: genCode's call, the far JMP that ensureRoom generates from one block to the next, emitJmp's far JMPs (eg, to a line in another block), genFuncExpr's calls to user-defined functions, and doChain's jump.  Return addresses and GOSUB frames are code selectors already, since the CPU pushes CS.
- **EXEC** (*done*, for COM and NE programs): a COM program's code and data are in one block (its PSP block), so load_program gives it CS from the block's code alias, and DS, ES, and SS from the block's data selector; the alias goes with the block when the program ends.  So a COM program can't write its own data through CS (or a DS or ES loaded from CS) in protected mode; BASIC-DOS's own tests use the DS (or SS) they start with, including for the far pointers they pass to DOS (eg, an EPB's command tail, which the kernel writes into while it parses it), and their interrupt handlers load DS from a copy of it (`data_seg`).  A program that sets a vector with DS:DX, as COM programs often do, would give it a data selector, so when DS is the program's PSP block, DOS_MSC_SETVEC uses the block's code alias instead (see mem_alias), which in real mode is the same segment.  An EXE file's relocations are paragraph arithmetic, so in protected mode they can only work if each 64K of the image has its own selector (as with CPU_MAP's consecutive selectors) and every relocated segment is a multiple of 64K from the start of the image, which isn't generally true; MZ EXE files would run only when the system is in real mode (or in virtual-8086 mode on an 80386), so in protected mode, load_program refuses them (with ERR_NOMEMORY, as it does for an EXE file too short for its header, which COMMAND reports as "Unable to load X"), rather than fault in the kernel.  An NE ("new executable") file, however, lists each segment's type (code or data) and size, and its relocations refer to segments by number, so in protected mode, load_program gives an NE program to `load_ne` (neload.asm, which follows `dos_fault` in the kernel's protected-mode-only code): each segment gets its own block (DGROUP's includes the heap and stack sizes in the NE header), which the new PSP owns, and its own selector (for a code segment, the block's code alias), whose limit fits the segment exactly, and each relocation gets the selector (or far pointer, or offset) it refers to.  It loads only programs marked PROTMODE, with FIXED segments, no imports, and only internal relocations, and it starts them with DS and ES addressing the PSP, as an MZ program starts; anything else gets ERR_NOMEMORY ("Unable to load X").  A program that does segment arithmetic or writes through a code segment still faults (and DOS ends it, since dos_fault accepts a fault in any block the program owns).  `TESTS\BIN\PRIMES.EXE` is an NE program, linked by LINK4 (see `tests/primes/PRIMES.DEF` and the [build tools](../../../software/src/tools/README.TXT)), with the real-mode program as its MS-DOS stub, so it runs in either mode.  LINK4 makes a segment code only if its class is `CODE`, requires a DGROUP, and without a `STUB` line, writes an MS-DOS header with no program at all, which real mode would run anyway (and crash).

#### DEF SEG, PEEK, and POKE {#defseg}

DEF SEG accepts any segment, which in protected mode isn't a selector, so it's mapped (*done*):

- **DEF SEG with no segment** (BASIC's own data, ie, the heap) stays as it is, readable and writable.
- **Any other segment** gets a selector for its 64K from the kernel (DOS_UTL_MAPSEG; see [Utility Functions](../util/#memory)), which each session keeps one of (the next call frees it): writable for video memory (A000h through BFFFh), and read-only (MEMF_RDONLY + MEMF_USER) everywhere else, including low memory (eg, segment 0 or 40h, for the BIOS data area) and the ROMs, so PEEK works, but POKE is an "Illegal function call" (POKE checks the selector with VERW, which it runs only in protected mode, when its CS, a code alias, isn't CODE_DS).
- **Segments that belong to the session** (eg, blocks that its programs allocated) could later be writable, too, once a BASIC program can get one (eg, with VARSEG); today, the only segment that BASIC-DOS gives a BASIC program is DEF SEG's default.
- In real mode, none of these restrictions apply, so programs that PEEK and POKE BIOS data or video memory keep working there.

#### Running Programs at Ring 3 {#ring3}

The goal is to run programs (COMMAND.COM, its BASIC programs, and COM programs) at ring 3, with CPU$, the drivers, and the kernel at ring 0, so that a program can only use the memory it's given, and can't use privileged instructions.

*Done*:

- **A TSS** (SEL_TSS, in the [system area](#sysarea)), which CPU_PMODE loads (LTR).  Only its ring 0 stack (SS0:SP0) is used: when an interrupt or exception takes ring 3 code to ring 0, the processor switches to that stack, and pushes the ring 3 SS and SP before the interrupt frame (FLAGS, CS, and IP), which an IRET to ring 3 pops again.  CPU_SETSTACK sets the stack; until then, it's 0:0, so nothing can run at ring 3.  BASIC-DOS never switches tasks, so the rest of the TSS stays zero.
- **Gates**: software interrupts (03h-05h, 10h-6Fh, and 80h-FFh) have DPL 3 gates, so ring 3 code can issue them (eg, INT 21h, or INT 10h, which `sw_int` reflects to the ROM at ring 0), and so does INT 0 (FPU$ signals a divide error with it), but other exceptions and IRQs have DPL 0 gates, so an INT for one of them at ring 3 is a general protection fault (with the gate's IDT entry as the error code, eg, 6Ah for INT 0Dh).  DDINT_SETVEC keeps each gate's DPL (it used to make every gate it set DPL 3).
- **FPU$** (see [Floating-Point Interface](../fpu/)): its functions are mapped with conforming code selectors (MEMF_CONFORM), so the kernel (for sprintf's `%f`) and programs at ring 3 (eg, COMMAND.COM's BASIC code) can call them, through the same FPUTBL, and they run at the caller's ring.  They no longer disable interrupts (which ring 3 code can't do, with IOPL 0); instead, the kernel saves and restores each session's FPU state when it switches sessions (`init_fpu` and `scb_switch`), and resets the FPU when a program ends.  Testing that (two sessions summing square roots at the same time) exposed a PCjs bug: its FRSTOR marked all 8 registers in use (and checked them for exceptions), so the next FLD overflowed the stack; fpux86.js now restores the tags as saved.
- **CPUTEST** runs code at ring 3 in protected mode, through DPL 3 aliases (MEMF_USER) of its PSP block, with a ring 0 stack of its own: a call to FPU$'s FPU_DTOA (if FPU$ is loaded) must run at ring 3, an INT 21h must reach DOS and return to ring 3, an INT 0 must reach a handler that CPUTEST installs, and an INT 0Dh must fault, which CPUTEST's fault handler (CPU_SETFAULT) takes as its way back to ring 0.

- **Programs at ring 3** (in protected mode, unless CONFIG.SYS has `RING=0`; see [CONFIG.SYS](../../bdman/cfg/#ring)): every session's first program (eg, COMMAND.COM) and the programs that EXEC loads and starts (COM and NE programs, including those that COMMAND.COM runs, which it loads with EXEC1 and starts with EXEC2) run at ring 3.  The code is in ring3.asm, which, like `dos_fault` before it, is resident only in protected mode; `set_fault` reads the RING line, setting `prog_user` (MEMF_USER) and `sprintf_hook` unless it's `RING=0`, and the rest of the kernel tests `prog_user`, so real mode (and RING=0) pays only a few bytes per hook.
  - **Selectors**: while psp_exec or scb_load loads a program (`load_user` is MEMF_USER), DOS_MEM_ALLOC gives its blocks DPL 3 (MEMF_USER) selectors, in the session's own LDT (MEMF_LDT; see below), with RPL 3 (so that a program can load one into SS, eg, `push ds` and `pop ss`, or an NE program's `mov ss,DGROUP`), as it does for any ring 3 caller (the RPL of REG_CS) when nothing is being loaded.  CPU$ gives a block's cached code alias the block's DPL (see CPU_ALIAS), so DOS_UTL_ALIAS and NE code segments follow.  `mem_alias` returns the alias with RPL 3 during a ring 3 load, or for a ring 3 caller, so a ring 3 program's CS (in PSP_START) has RPL 3, which is how psp_exec, for EXEC and EXEC2 alike, knows to start the program at ring 3 (`r3_start`); RPL 3 also keeps the PCjs emulator, which takes a gate's new CPL from its selector's RPL (a real 80286 uses the target's DPL), from entering a ring 3 program's interrupt handler (eg, one it set with DOS_MSC_SETVEC) at ring 0.
  - **Ring 0 stacks**: a ring 3 program's ring 0 stack is its parent's stack, just below the parent's REG_FRAME, where the parent waits for it to end, which the parent's PSP_STACK records.  `r3_start` copies the program's initial REG_FRAME there (load_program builds it on the program's own stack), followed by the program's SS (RPL 3) and SP, for the IRET to ring 3, and sets the ring 0 stack (CPU_SETSTACK) to the end of the copy; whenever another program becomes current (psp_term, when a program ends, and `scb_switch`), `r3_sp0` sets it from that program's parent's PSP_STACK.  So nested programs need no stacks of their own, and every DOS call, interrupt, and fault from a ring 3 program runs on its parent's stack.  A session's first program has no parent, so each session also has a ring 0 stack of its own (R3_STACK_SIZE, 1K), in a block that sysinit allocates for all of them (`init_sess`, whose selector is `r3_stseg`; if there's no room, programs run at ring 0): `r3_top` returns the top of a session's stack, scb_load's `r3_load` moves a ring 3 first program's initial REG_FRAME there, and `r3_sp0` uses it for a program without a parent.  sysinit_tail, which starts the first session without going through scb_switch, sets that session's LDT and ring 0 stack itself, with CPU_SETLDT and CPU_SETSTACK: it runs in sysinit's relocated block, so it can't make near calls into the resident kernel (an earlier version called `r3_sp0` and `r3_setldt` anyway, which worked only while a stale copy of them happened to lie below that block).
  - **An LDT per session**: a ring 3 program's selectors are in its session's own LDT (MEMF_LDT), so a program can't name another session's memory.  CPU_SETLDT makes a session's LDT the active one, and the kernel calls it (through `r3_setldt`, except in sysinit_tail) whenever the current session changes: in `scb_switch` (before `r3_sp0`, since the session's PSP selector is in that LDT), when sysinit_tail starts the first session, when psp_term returns to a parent (which may be in another session), and around scb_load, which makes the loaded session's LDT active while it loads the program (so its memory goes there) and restores the caller's afterward.  Since the caller's command line is in the caller's LDT, scb_load first copies it to a kernel buffer (`stage_cmdline`, into `cmdline_buf`, CMDLINE_MAX bytes), and leaves DS and ES pointing at the kernel's data, which stays addressable in any LDT.  Selectors repeat from one session's LDT to the next (eg, every session's first program has PSP selector 0007h), so CPU$ records in each block's PMB_LDT which LDT was active when its owner was set, and CPU_FREEALL frees an LDT owner's blocks only from the active LDT; before that, a session's program ending (or failing to load) freed every block whose owner had the same selector, including COMMAND.COM's in session 0.
  - **The caller's stack**: a DOS call from ring 3 has the caller's SS:SP after REG_FL, not in SS:SP, so for a ring 3 caller, utl_printf and utl_sprintf call `r3_sprintf` (through `sprintf_hook`), which runs sprintf on the caller's stack (as it runs in real mode), through a DPL 0 alias of the caller's SS (since SS must be DPL 0 at ring 0), with a copy of the REG_FRAME just below the parameters and BP pointing at the copy, since a call can pass any number of parameters (eg, HEXDUMP's PRINTF USING of 19 values, at 3 words each; when r3_sprintf copied at most 32 words of them, sprintf read the rest from its own stack, and HEXDUMP faulted in the kernel).  Without a free descriptor for the alias, it copies the REG_FRAME and up to 32 words of parameters (within the caller's stack segment's limit, from LSL) below our stack instead.
  - **CALL 5**: SEL_CALL5's call gate is DPL 3, and when the caller is at ring 3, `dos_call5` goes to `r3_call5`, which pops the near CALL's return address from the caller's stack and rebuilds the frame as an interrupt from ring 3.
  - **CTRL-C and critical errors**: a session's CTRL-C (INT 23h) or critical error (INT 24h) handler whose CS has RPL 3 (a ring 3 program's) runs at ring 3, on the stack of the program that called DOS.  An IRET takes it there, with a return address on that stack pointing at `r3_stub`, an INT 22h, through `r3_code` (a DPL 3, execute-only alias of the kernel's code, which `set_fault` creates), and when the handler returns, dos_exit (INT 22h, which no program issues, since INT 22h is only a vector) goes to `r3_cbret`.  For a critical error, dev_error calls `r3_error` (on the hard error stack), which points the handler's BP:SI at a copy of the device header on the program's stack, since a ring 3 handler can't read the driver's memory, and lowers the program's ring 0 stack to dev_error's caller's stack while the handler runs (the session is locked, so no session switch can change it), so that the handler's own DOS calls (eg, to prompt for a response) don't disturb the call in progress; `r3_cbret` restores it and returns the handler's AL to dev_error, and a CTRL-C inside the handler still ends it with ABORT (`r3_cbabort`).  For CTRL-C, msc_sigctrlc calls `r3_ctrlc` once it has built the REG_WS frames, so that its RETF goes to `r3_iret`, which IRETs to the handler, with the DOS call's IP, CS, and FLAGS on the program's stack after the handler's return address; when the handler returns, carry set ends the program (EXTYPE_CTRLC), as at ring 0, and otherwise the DOS call restarts with the handler's registers, and the IP, CS, and FLAGS from the program's stack, which the program could have changed, so the CS gets RPL 3 and the FLAGS get IOPL 0, NT clear, and interrupts on.
  - **DEBUG.COM** (as a driver, at ring 0): when it stops ring 3 code, it takes the code's SS:SP from the interrupt frame (`frame_ptr` records where the frame's FLAGS end), so R shows them (and D SS:SP dumps the program's stack), and `resume` and `sim_int` (for GT) store them back in the frame, for the IRET to ring 3 (or for the ring 0 handler that GT passes a fault to); `chk_ring` tells when the stopped code ran at another ring than DEBUG's own.
  - **Vectors**: the IDT is shared by every session and by ring 0 code, so a ring 3 program's handler can't go in a gate: ring 0 code can't call it (eg, the kernel's own INT 21h calls, once a program hooks INT 21h), another session's LDT doesn't have its selector, and its far JMP to the previous handler (a DPL 0 selector, from DOS_MSC_GETVEC) would fault.  So when a ring 3 program sets a vector (other than INT 22h-24h, which each session has its own of), `r3_setvec` (from msc_setvec) records the handler in an RVEC (see ring3.asm), one of R3_RVECS, and the RVEC's own code (a CALL to `r3_reflect`) becomes the gate: from ring 3, in the RVEC's session, `r3_reflect` pushes the caller's FLAGS, CS, and IP on its stack, as its INT would have, and IRETs to the handler, at ring 3; from anywhere else, it enters the previous handler with the interrupt's frame.  When a ring 3 program gets a vector that isn't one of its session's handlers, `r3_getvec` (from msc_getvec) returns the address of an RVEC's stub, an INT 22h in `r3_stubs`, whose selector (`r3_vsel`, which `set_fault` maps) is a DPL 3 readable code selector for just those stubs, since the program gets the address in ES:BX, and `r3_code` (execute-only, for the whole kernel) can't be loaded into ES.  Jumping to a stub (or calling it, after a PUSHF) takes `r3_cbret` to the previous handler, with the IP, CS, and FLAGS on the program's stack, as if the interrupt had gone straight to it, so DOS returns to the original caller; setting the vector to a stub restores the handler it chains to.  psp_term frees a program's RVECs (`r3_endvec`), taking any that's still a gate out of it, and so do the RVECs that chained to one.  So IOERR works at ring 3: its INT 21h hook sees the calls of the BASIC program and VI that it runs, chains the rest to DOS, and the kernel's own INT 21h calls go straight to DOS.
  - **COMMAND.COM**: besides its own ring 0 stack (above), it needed DPL 3 selectors for video memory (the identity selectors A000h-B800h are DPL 3 now, so the selector from VKD$'s IOCTL_GETMODE works at ring 3), and kernel functions for what it used to read itself: the tick count (RANDOMIZE, SOUND, and PLAY read the BIOS's at 40h:6Ch; now DOS_UTL_GETTIME with AL = 1 returns it), MEM's total memory (DV_MEM_SIZE, in the kernel's data; now DOS_MSC_GETVARS returns it in AX, too), and RESTART's session list (which read a program's name from PSP-1, as if it were a real-mode MCB; now DOS_UTL_QRYSCB copies the session's console and program names into the caller's buffer).  And fpuOp reaches FPU$'s conforming functions with a RETF, which requires the target selector's RPL to be at least the CPL, so getFPUFunc gives the selector COMMAND's RPL (a far CALL to conforming code has no such rule, which is why child programs already worked).
  - **Tested** (DEBUG build, 2Mb PC AT): FPUTESTS (PRINTF and FPU$ from ring 3), DOSTESTS (EXEC, sessions, CALL 5, and the file and handle tests), FCBTESTS, FAULT (`CPU fault 0D` and `Division error` at a CS with RPL 3, ending the program), and NE programs (PRIMES, and a test with two code segments, far calls and a far pointer between them, and a fault in the second, which ends the program) all work at ring 3, as do HARDERR (its own INT 24h handler, for RETRY, FAIL, IGNORE converted to FAIL, the device header copy, and ABORT; at ring 3, it skips its tests that need an INT 13h hook, since FDC$ issues INT 13h at ring 0), a CTRL-C handler that continues (the DOS call restarts and reads the next key), PRIMES' CTRL-C handler (which ends it), and DEBUG.COM's driver, stopping a ring 3 program at an INT 3 (R, D SS:SP, T, and G).  With COMMAND.COM at ring 3, too (the default), so do the BASIC tests (STRFUN through PRTUSING, including CMDS' pipes and HEXDUMP), MOVES, ATTRS, IOERR (whose INT 21h hook is reflected), RESTART and MEM, sessions loaded into other sessions' LDTs (DOSTESTS' session load test, and three sessions on one machine), and PRIMES and the two-segment NE test; mmutest's `r3` machine runs all of these, and its `pm` machine (`RING=0`) and real-mode machines still pass every test.

*Remaining*:

- **I/O**: programs keep IOPL 0 (FL_DEFAULT), so ring 3 code can't use IN, OUT, CLI, or STI, and drivers own the hardware; COMMAND's SOUND already started its sounds through CLOCK$ (DOS_UTL_SOUND, which CLOCK$'s timer handler turns off), and PLAY, which turned the speaker on and off itself (ports 42h, 43h, and 61h), now does too, starting each note with DOS_UTL_SOUND for 65535 ticks (about an hour, so effectively until it's turned off) and ending it with a PIT divisor of 0; there's no BEEP statement yet.
- **Vectors at ring 0**: a ring 3 program's handler sees only the interrupts that ring 3 code in its own session issues, so a hook of an interrupt that ring 0 code issues (eg, INT 1Ch, from the ROM's timer handler, or INT 13h, from FDC$, which HARDERR's tests need, so it skips them at ring 3) never runs; running it would need an upcall like the critical error handler's.  And there are 8 RVECs (R3_RVECS) for all sessions; with none free, a vector is set (and returned) as it was before.
- **DEBUG.COM as a program**: run as a program (eg, from COMMAND.COM), DEBUG.COM is itself at ring 3, where it can't call CPU$ (DDINT_CPU), which it uses for its system registers and every memory access, so only its driver can debug ring 3 programs for now (or with `RING=0`, DEBUG.COM as a program works as before).  CPUTEST also calls CPU$ directly, so it too needs `RING=0`.
- **Table sizes**: each session's LDT has 96 entries, and a block keeps the selectors it was allocated with when CPU_REALLOC shrinks it, so a program loaded into the largest free block (as load_program does) holds one LDT selector for every 64K of that block (eg, 16 for COMMAND.COM, loaded into a 1Mb block); giving back the selectors that a shrunken block no longer needs would leave more room.

#### Phases {#phases}

1. **Done**: CPU$ (processor detection, A20, the arena, GDT, IDT, and LDT, a self-tested switch to protected mode and back, and the CPU_* functions, all called in real mode), CPU_TYPE and DDINT_CPU in low memory, `--ram=2M` in pc.js, and CPUTEST.COM (in TESTS\MISC on test disks), which prints the arena and checks every function.
2. **Kernel interfaces**: CPU$ managing all memory in either mode, with CPU_REALLOC and CPU_MOVE (*done*), devinit and sysinit claiming, mapping, and moving their memory with them (*done*; see [Claiming Memory at Boot](#claiming)), and the kernel's memory functions (DOS_MEM_ALLOC and friends, freeing a program's blocks when it ends, and MEM) and DEBUG's DM using CPU$, with each block's owner, type, and name kept by CPU$ (*done*), allocating from all of memory, conventional and extended alike (*done*).
3. **COMMAND.COM in extended memory, from real mode**: eg, keeping the copy of the transient part, or large arrays, in extended memory with CPU_MOVE.
4. **Interrupts in protected mode** (*done*, so far): CPU$ moves the master PIC, reflects software and hardware interrupts to the ROM BIOS at ring 0, and keeps the drivers' handlers in the IDT (see [Protected-Mode Interrupts](#interrupts)).  Next: trying the rest of the BIOS functions that the drivers use.
5. **A protected-mode kernel**: the segment-arithmetic inventory and fixes (*in progress*; see [Mode-Independent Code](#modeless) and [COMMAND.COM](#command)), staying in protected mode after CPU$ initializes (*in progress*: the drivers, the kernel, and COMMAND.COM all start in protected mode; see [Protected-Mode Initialization](#pminit)), code aliases for COMMAND's generated code and for EXEC (*done*, for COM and NE programs), programs at ring 3 (*done*, but for the programs listed under [Running Programs at Ring 3](#ring3)'s *Remaining*: unless `RING=0`, COMMAND.COM and every program run at ring 3, with each session's programs in its own LDT), and running DOS programs in real mode (80286) or virtual-8086 mode (80386).

### Open Questions

- **The HMA**: putting the system area in the HMA costs no conventional memory and is reachable in both modes, but A20 stays enabled, so besides the CALL 5 trampoline, programs that depend on wrapping at 1Mb could break (eg, EXEPACK-compressed programs loaded in the first 64K report "Packed file is corrupt").
- **Owners**: should PMB owners be PSPs (freed when a program ends) or sessions?
- **Table sizes**: 128 PMBs, 256 GDT entries, and 32 LDTs of 96 entries each are guesses (see [Running Programs at Ring 3](#ring3)'s *Remaining* for how quickly a session can use up its LDT).
- **Identity selectors**: the GDT has them only for video memory and the ROMs (A000h-F800h, every 800h), so a ROM segment that isn't a multiple of 800h (eg, F600h, the PC's ROM BASIC) can't be reflected to, and DMA buffers more than 64K above 400h have none yet (FDC$ sends such diskette transfers through its own buffer); a few more (or temporary ones) may be needed.
